## SDD가 필요한가? — 답

필요하다. 다만 **문서가 아니라 채점표**로 쓴다.
- 마일스톤마다 스펙 1개, 그 안에 번호 붙은 AC 표 하나.
- AC 하나 = 이름이 `AC-n`으로 시작하는 테스트 하나 이상.
- `pnpm verify`가 테스트 결과를 AC 표로 되돌려 보여준다. 스펙이 곧 진행 상황판이다.
- 버린 것: 기능마다 몇 페이지짜리 스펙 문서. 코드보다 맞춰야 할 글이 많아진다.

## 하네스 — Codex 하네스 키트를 Claude Code로 옮김

단테가 이미 만든 [codex-harness-kit](https://github.com/dante01yoon/codex-harness-kit)의 역할 다섯 개(알림·차단·검증·통지·중단)를 그대로 가져와 Claude Code 훅으로 다시 만들었다. 강의 흐름이 이어진다: "책에서 Codex로 손으로 만든 하네스 → 키트 → 같은 철학을 Claude Code 프로젝트에".

| 역할 | 이 레포에서 |
|---|---|
| 알림 | `AGENTS.md`: 스펙이 완료 기준, 스펙 세션과 구현 세션 분리, 막히면 `BLOCKED:` |
| 차단 | PreToolUse 훅 `guard.mjs`: spec·acceptance·fixtures·harness·.claude 수정 거부 |
| 검증 | Stop 훅 → `pnpm verify`: 계약 드리프트, 타입, 테스트, AC 표 |
| 중단 | 3번 실패하거나 `BLOCKED:`로 답하면 멈출 수 있음 |
| 측정 | `measure-glb.ts`: "크기가 맞나?"를 cm 숫자로 바꿔줌 |

**강의 포인트:** "에이전트에게 일을 시키기 전에 채점기부터 만든다. 그리고 채점기도 채점한다." → `harness/self-test/`가 가드의 차단·허용 표와 GLB 측정기를 크기를 아는 fixture로 검사한다.

**강의 포인트 2:** 스펙 세션(`ROOMFIT_SPEC_SESSION=1 claude`)과 구현 세션을 나눈다. 구현 에이전트는 시험지(acceptance)와 정답지(fixtures)를 고칠 수 없다.

## 후반 — ADR-0002 확정 (2026-10-18)

**단테:** "트레이드오프 해서 적절한 걸로 선택해. 확장성 좋은 걸로." → 결정을 에이전트에게 위임.

**처음 선택지:** 축별 맞춤(치수 정확, 늘어날 수 있음) vs 균일 맞춤(비율 유지, 바닥 면적 틀어짐). 둘 중 하나를 고르면 나중에 바꾸기 비싸다.

**결정:** 질문을 바꿨다. "어떻게 맞출까"가 아니라 **"무엇이 진실인가"**.
- 표기 치수가 진실이다. 충돌·방 경계·스냅은 `asset.dimensions`만 쓴다. 메시가 어떻게 생겼든 "들어가나?"의 답은 맞다.
- 메시 맞춤은 보이는 모양의 문제이고, 모드로 기록한다: `exact`(기본, 축별) / `uniform`(비율 유지). 새 모드는 enum에 추가만 하면 된다.
- 모든 맞춤은 리포트(축별 배율, 왜곡 = 최대/최소 배율)를 내고, 1.15를 넘으면 표시해서 에디터가 `uniform`이나 재생성을 권할 수 있게 한다.

**강의 포인트 4:** 트레이드오프에서 둘 중 하나를 고르기 전에, 두 관심사가 왜 묶여 있는지 먼저 본다. 묶임을 풀면 선택이 되돌릴 수 있는 설정값으로 바뀐다.

**스펙 세션에서 한 일:** AC-3·AC-4를 active로 올림, AC-11(uniform)·AC-12(리포트) 추가, `fitGlb` 인터페이스를 스펙에 명시, 비율이 틀어진 fixture(`generated-squashed-box.glb`, 100×30×45cm) 추가, 계약에 `fit: { mode, distortion }` 추가.

**의도된 빨간불:** `pnpm verify` → `VERIFY FAIL`. AC-3·4·11·12가 `NO TEST`, `packages/fit`이 없어서 타입 에러. 테스트(시험지)는 있고 구현은 없는 상태로 커밋한다. 첫 구현 세션은 이 빨간불을 초록으로 바꾸는 것이고, 그때 Stop 훅이 실제로 에이전트를 돌려보내는 장면을 녹화할 수 있다.

## SDD를 어떻게 하고 있나 — 단테의 질문

"너는 SDD 어떻게 하고 있어? 무슨 스킬 써?" → 솔직한 답: **전용 스킬이나 도구(spec-kit 등)를 쓰지 않았다.** 이 레포의 관례로 직접 만들었다.
- 스펙 = `spec/M<n>-*.md`의 AC 표 (상태: active / planned / manual)
- 시험지 = `acceptance/`의 테스트, 이름이 `AC-n`으로 시작
- 채점 = `harness/verify.mjs`가 테스트 결과를 AC 표로 되돌림
- 권한 = 스펙 세션만 시험지·정답지를 고침(가드 훅)
- 결정 = ADR, 과정 = 이 저널

장점은 도구 의존이 없고 전부 `pnpm verify` 하나로 보인다는 것. 단점은 다른 프로젝트에 옮기려면 손으로 복사해야 한다는 것. 두세 번 반복해서 형태가 굳으면 스킬이나 키트로 뽑는다(codex-harness-kit처럼).

## 세션 03 — 에디터 스펙: "에이전트가 볼 수 있게" 만들기 (2026-10-18)

녹화: `docs/recordings/impl-02-placement.md` — 100초, 17턴, $0.86, Stop 훅 0회, 가드 0회. 이번에도 스펙 빈틈 2개를 보고해 옴(방 원점이 안 적혀 있음, `no-scene` fixture 없음) → 둘 다 스펙에 반영. `no-scene` 테스트는 추가하자마자 통과(구현이 이미 처리하고 있었음).

**결정 ADR-0004:** 에디터는 Vite + React + R3F. 핵심은 스택보다 **`window.roomfit` API 하나**다. UI 제스처, ComfyUI 브리지, e2e 테스트, 코딩 에이전트가 모두 같은 함수를 부른다.

**강의 포인트 7 — 캔버스는 에이전트에게 깜깜이다.** WebGL 캔버스에는 DOM이 없어서 에이전트는 "소파가 어디 있는지" 물어볼 방법이 없다. 그래서 상태를 묻는 API(`state()`, `scene()`)를 계약으로 먼저 정했다. OpenAI가 하네스 엔지니어링에서 말한 "앱을 에이전트가 읽을 수 있게(legible)"를 3D 에디터에 적용한 것. 실패하면 스크린샷과 trace를 남겨서 에이전트가 눈으로도 확인할 수 있다(하네스의 See 역할).

**스펙 세션에서 정한 숫자들:** 카메라 세로 FOV 50°, 천장 없음, GLB 로드 실패 시 표기 치수 상자로 대체, depth는 가까울수록 밝게(ControlNet depth 관례), normal은 카메라 기준 RGB=(n+1)/2(정면 = 128,128,255). 위에서 내려다보는 카메라로 소파 픽셀과 바닥 픽셀을 샘플링해 세 패스를 검사한다. 처음 고른 바닥 픽셀(8,8)은 FOV에 따라 방 밖일 수 있어서, FOV 45~60° 어디서든 바닥에 떨어지는 (83,96)으로 바꿨다. 테스트도 검산이 필요하다.

**하네스 확장:** `package.json`과 `playwright.config.ts`도 보호 대상이라 구현 에이전트는 의존성을 추가할 수 없다. 에디터 의존성(React, R3F, three, Playwright)은 스펙 세션에서 미리 넣었다. 더 필요하면 `BLOCKED:`로 요청해야 한다.

- 원인은 **스펙 세션(나)의 fixture 버그**였다. 상자 fixture의 삼각형이 안쪽을 향하고 노멀이 없었다. 에이전트는 fixture를 못 고치니까(가드), "생성 메시도 면이 뒤집힌 경우가 흔하다"는 판단으로 가구를 양면 렌더링 + 노멀 계산으로 처리하고, fixture를 고칠지는 스펙 세션에 넘겼다. → 스펙 세션에서 fixture 삼각형 12개를 바깥 방향으로 고침(검산 스크립트로 12/12 확인). 에이전트의 양면 처리는 실제 생성 메시에 대한 방어로 유지.
- macOS에서 Vite는 IPv6 `localhost`, Playwright는 `127.0.0.1`을 봐서 서버를 못 찾는 문제를 스스로 고쳤다.

**하네스 교훈:** 내가 스크린샷 찍으려고 띄운 개발 서버가 5179 포트를 잡고 있어서 다음 verify의 e2e가 0.5초 만에 실패했다. 코드 문제가 아니라 환경 문제. 사람(나)도 하네스 환경을 더럽힌다.

### poteto-mode(pstack)는 무엇을 했나 — 단테 요청으로 기록

**어떻게 들어오나:** roomfit 설정이 아니라 단테의 사용자 레벨 플러그인 pstack(0.9.36)의 SessionStart 훅이 **모든 세션**에 "파일 2개 이상·설계·원인 모를 버그면 `pstack:poteto-mode`를 켜라"를 주입한다. 사용자 지시(AGENTS.md)가 우선한다고 스스로 적혀 있다.

| 세션 | 작업 크기 | 스킬 로드 | 플레이북 읽음 | 서브에이전트 | 답변에 원칙 인용 |
|---|---|---|---|---|---|
| impl-01 | 파일 1개 | 안 함 | 0 | 0 | 없음 |
| impl-02 | 파일 2개 | 안 함 | 0 | 0 | 없음 |
| impl-03 | 파일 9개 | **함** | 0 | 0 | 없음 |

**poteto-mode가 요구하는 것(SKILL.md):** 코드 전 데이터 형태 결정, 함수 경계를 넘으면 `architect`로 설계안 비교, `feature` 플레이북은 "코드 작성은 서브에이전트에게 위임 — 필수", 답변에 원칙 인용, 커밋 전 `deslop`, 리뷰 전 `no-comments`, 긴 자율 작업은 결정 기록(show-me-your-work).

**실제로 관찰된 것:** impl-03은 스킬을 불러왔지만 그 안의 필수 절차(플레이북, 서브에이전트 위임, 원칙 인용, 결정 기록 파일)는 하나도 실행하지 않았다. 관찰 가능한 행동은 레포 규칙(AGENTS.md)과 하네스로 설명된다. 즉 **이번 세션에서 poteto-mode의 효과는 transcript상 확인되지 않음**(컨텍스트 소모만 확인). 말투·설계 습관 같은 미묘한 영향은 켜고 끈 비교 없이는 판단할 수 없다.

**소프트웨어 팩토리와의 관계:** pstack에는 팩토리형 플레이북이 있다 — `orchestrate`(코디네이터가 작업지시서로 수십 개 에이전트 운영), `autopilot-full`(PR당 담당 에이전트·worktree, 머지 전 swarm 독립 검증, 머지는 사람), `autonomous-run`(완료 조건까지 무인 반복). 하지만 이것들은 "autopilot this queue", "orchestrate" 같은 **명시적 요청**에 반응하고, 한 줄 구현 프롬프트로는 자동 실행되지 않았다.

**강의 포인트 8 — 전역 설정은 실험 변수다.** 같은 레포·같은 하네스라도 사용자 레벨 플러그인이 세션마다 지시를 주입한다. SDD 도구 비교나 방법론 비교를 할 때는 양쪽을 같은 전역 설정으로 돌리거나 사용자 설정을 빼고(`--setting-sources project`) 돌려야 공정하다. 비교 변수 후보: ① 레포 하네스(우리 방식) ② SDD 도구(spec-kit 등) ③ 플러그인 팩토리(pstack `orchestrate`/`autopilot-full`) ④ poteto-mode 켬/끔.

**강의 포인트 9 — "레포에 박은 하네스" vs "프롬프트로 든 프로세스".** 우리 방식은 검증 게이트가 코드(훅·verify)라서 에이전트가 무시할 수 없다. 플레이북 방식은 프로세스가 텍스트라서 에이전트가 건너뛸 수 있다 — impl-03이 `feature` 플레이북의 "필수" 위임을 건너뛴 것처럼. 둘은 경쟁이 아니라 층이다: 프로세스는 프롬프트로, 합격 기준은 코드로.

## 세션 05 — 노드팩 스펙: 진짜 ComfyUI를 하네스에 넣기 (2026-10-18)

**ADR-0005 핵심:**
- 맞춤을 GLB 파일이 아니라 ComfyUI의 MESH(정점 텐서)에서 한다. 코어 3D 노드들이 MESH를 주고받으니 `RoomfitFitMesh`를 생성과 `SaveGLB` 사이에 끼우기만 하면 된다. Python에 GLB 파서가 필요 없다.
- 같은 규칙을 TS와 Python 두 언어로 구현하고, **같은 fixture·같은 기대값**으로 검사해 언어 간 어긋남을 AC 실패로 잡는다.
- 워크플로 JSON은 **고정한 노드 카탈로그**(실제 로컬 ComfyUI `/object_info`에서 뽑은 893개 클래스 + 우리가 쓰는 19개 노드 상세)로 린트한다. 클래스 존재, 필수 입력, 링크 대상, 링크 타입, 콤보 값까지. 린터는 하네스 소유이고 자체 테스트 7개가 있다.
- 워크플로의 입력 노드는 `_meta.title = "roomfit:*"` 태그로 찾는다. 사용자가 ComfyUI 캔버스에서 워크플로를 고쳐도 에디터가 계속 몰 수 있다.
- **진짜 ComfyUI를 하네스에서 띄운다.** 단테의 로컬 ComfyUI를 CPU로, `--base-directory .harness/comfy-base`로 격리해서. 체크아웃은 건드리지 않는다. 노드 등록과 라우트 서빙은 모델 없이 확인 가능.

**강의 포인트 10 — "모델 없이 검증할 수 있는 것"을 최대로.** GPU·모델이 필요한 부분(실제 3D 생성, 실제 렌더)은 AC-10 데모 하나로 몰고, 나머지(노드 시그니처, 워크플로 배선, 맞춤 수학, 라우트)는 전부 CPU 하네스에서 자동 검증한다.

## 세션 06 — 노드팩 구현과 AC-10 실제 데모 (2026-10-18)

**구현 세션 impl-04-nodepack:** 260초, 29턴, $1.48, Stop 훅 0회, 가드 0회. Python 노드팩·워크플로 2개·프롬프트 빌더. 내가 다시 돌린 verify: 게이트 7개(실제 로컬 ComfyUI CPU 기동 포함) 전부 PASS, active AC 20개 PASS. 에이전트가 이번에도 빈틈을 보고: float32 노이즈 때문에 Python은 측정 크기를 1µm에서 반올림하는데 TS는 안 한다 → 스펙 열린 질문으로 기록.

**AC-10 실제 데모 (스펙 세션, 내가 직접):** 상품 사진(Z-Image) → 3D(TRELLIS.2, Cloud) → `fitGlb` → 에디터 배치·충돌·벽 체크·되돌리기(Playwright 영상) → 깊이 패스 → Cloud 렌더. 28초 영상 `docs/recordings/media/roomfit-demo.mp4`, 기록 `docs/recordings/demo-ac10.md`.

**실제 데이터가 스펙을 고친 순간들 (강의 포인트 11):**
1. 생성 모델 크기가 **94×41×38**로 나왔다. `exact` 맞춤 후 정확히 200×85×90, 왜곡 1.157로 경고 기준(1.15)을 막 넘어 표시됨. ADR-0002의 "치수가 진실, 모양은 모드" 설계가 실제 데이터에서 바로 쓸모를 증명.
2. **정면 방향이 틀렸다.** 스펙은 −Z라고 했는데 실제 생성 모델은 +Z(glTF 관례). 테스트에 걸리는 곳이 없어서 실제 데이터를 보기 전까지 아무도 몰랐다 → ADR 수정, "방을 향해 놓기" 기능 때 AC로 만들기로.
3. **SDXL depth ControlNet이 Cloud 카탈로그에는 있는데 실행 검증에서 매번 거부**(과금 없음, 2회). Comfy 공식 템플릿이 쓰는 Z-Image Turbo + Fun Union ControlNet으로 워크플로를 바꿨다. 이때 하네스 린터가 로컬에 설치된 모델 목록으로 콤보를 검사해서 `ae.safetensors`를 거부할 뻔 → 모델 파일 입력(`*_name`)은 콤보 검사에서 제외하도록 스냅샷 도구 수정.
4. **데모 스크립트 버그:** 소파를 x=150으로 밀었는데 에디터가 "문제 없음"이라고 했다. 에디터가 맞았고 내 숫자가 틀렸다(회전한 소파 반폭 45 → 195 < 210). x=180으로 고침.

**강의 포인트 12 — 같은 실수가 두 번이면 구조로 막는다.** 내가 띄워둔 개발 서버가 5179 포트를 잡아서 e2e가 실패한 게 두 번째다. 이번엔 메모 대신 `verify`에 포트 점검을 넣었다: 포트가 차 있으면 어떤 PID인지와 끄는 명령을 알려준다. 일부러 포트를 점유해서 경고가 뜨는 것까지 확인. (poteto의 "Encode Lessons in Structure" 원칙과 같은 생각.)

**M1 상태:** 자동 검증 AC 20개 PASS, AC-10 수동 데모 완료. 구현 세션 4번 합계 약 17분, $5.88. 네 번 모두 Stop 훅·가드 발동 0 — 에이전트가 끝내기 전에 스스로 verify를 돌렸고, 막힐 땐 우회 대신 보고했다.

## 세션 07 — "실제 시연영상": 에디터가 직접 Comfy Cloud를 부르게 (2026-10-18)

**단테:** "실제 시연영상 찍어봐 컴피 클라우드 써서."

**판단:** AC-10 데모는 Cloud 호출을 내가(에이전트 도구로) 했고 영상은 정지 화면을 이어 붙였다. "실제 시연"이 되려면 **제품 자체가** Cloud를 불러야 한다 → 에디터 ↔ ComfyUI/Comfy Cloud 브리지를 M1에 추가(AC-21~27, ADR-0006).

**정정:** AC-10 데모의 3D는 TRELLIS.2가 아니라 같은 템플릿의 **Pixal3D 분기**(스위치 기본값 false)로 생성됐다. Cloud가 실제로 실행한 API 그래프를 받아 보고 알았다.

**결정:**
- API 키는 브라우저에 절대 안 간다. 로컬 개발 서버 프록시가 `X-API-Key`를 붙이고, `/api/view`의 302 리다이렉트는 서버가 키 없이 따라간다(Cloud 문서의 경고). AC-25가 브라우저 요청·서빙된 코드·스토리지 리다이렉트까지 검사.
- Cloud는 우리 커스텀 노드를 못 돌리니 맞춤은 브라우저에서(`fitGlbBytes`). 레이아웃에는 맞춘 메시 대신 **원본 위치(`comfy-output:`) + 치수 + 모드**를 저장하고 열 때마다 다시 맞춘다. 맞춤이 순수 함수라서 가능한 설계.
- Cloud 워크플로는 Comfy 공식 템플릿을 Cloud가 실제 실행한 그래프에서 가져와 고정(미리보기 노드 제거, `SaveGLB`로 출력 형식 확정). 수정본을 Cloud에서 실제로 한 번 더 돌려 확인(job `ad9f4464…`).
- 하네스: Comfy Cloud 흉내 서버(`fake-comfy.mjs`) — 요청 기록, 키 요구, 작업 상태 진행, 스토리지 리다이렉트까지. 포트 점검에 8199/8197 추가.

**막힌 것:** 진짜 Cloud로 녹화하려면 단테의 Comfy Cloud API 키(유료 구독)가 필요하다. 에이전트가 만들 수 없는 것 → 사람에게 요청.

## 세션 08 — 실제 Cloud 시연 녹화와 홈 스튜디오 (2026-10-18)

**AC-27 실제 녹화:** 단테가 넣은 키로 `pnpm web:dev`를 Comfy Cloud에 연결 → 에디터 화면에서 사진 넣고 Generate 3D → Cloud 3D 생성 62초 → 맞춤(왜곡 1.13) → 배치 → Render → Cloud 렌더 10초. 전체 90초, 영상 36초(대기 구간 8배속 표시). 키는 서버 프록시에만 있고 브라우저에는 안 간다(AC-25로 보장). 기록: `docs/recordings/demo-ac27-cloud-live.md`.
- 작은 사고: 단테가 안내문의 예시 값 `여기에_키`를 그대로 넣었다. 키 값을 출력하지 않고 "예시 문구인지"만 검사해서 알려줬다. 키를 다루는 대화의 원칙: 값을 보지 않고 상태만 확인한다.

**M2 홈 스튜디오 (단테: "MengTo 레퍼런스처럼"):**
- 스펙 세션: 계약에 plan 방(벽 중심선·문/창 개구부·바닥 구역) 추가, 14×10m 데모 하우스 fixture(6개 방, 가구 15개), 장면 프리셋 표(Reading/Work/Movie/Evening의 태양 고도·색온도·세기), ADR-0007(한 에디터·두 뷰, 네트워크 자산 금지).
- impl-07 (363초, $1.74): plan 방 배치 규칙(구역 밖·벽 관통·천장) + 에디터 렌더. **또 `BLOCKED:`** — 내가 계약의 `outOfBounds.reason`에 `hits-wall`을 안 넣었다. 에이전트는 다른 값으로 바꿔치기하는 우회를 거부하고 줄 번호를 보고.
- impl-08 (749초, $2.95): 스튜디오 뷰. 그림자·AO·ACES 톤매핑·브라우저에서 그린 바닥 텍스처·로우폴리 나무·진입로·하단 알약 바. 스스로 Work/Evening 스크린샷을 찍어 레퍼런스 설명과 비교. 저녁 프리셋에서 방마다 따뜻한 불빛.

**강의 포인트 13 — 스펙 작성자(나)의 실수가 계속 시험지에서 걸린다.** 세션 5(테스트 타입 오류), 세션 7(계약 누락) 모두 에이전트가 고치지 않고 정확히 보고했다. 시험지 보호가 사람의 실수까지 드러내는 장치가 된다.

**강의 포인트 14 — "보이는 것"을 테스트하는 방법.** 스튜디오의 미적 품질은 자동 테스트로 못 잰다. 대신 측정 가능한 부분만 계약으로: 카메라 고도각, 프리셋별 조명 값 표, 저녁이 낮보다 15% 이상 어두운지(휘도), 네트워크 요청 0. 나머지는 스크린샷과 사람의 눈(AC-35 수동).

## 세션 09 — 진짜 가구 15개를 Cloud에서 만들었더니 (2026-10-18)

**단테:** 크레딧 사용 승인("Yes, go ahead … 14 furniture pieces").

**실행:** 상품 사진 14장(Z-Image, 배치 1회) → 3D 15개(소파 포함)를 **roomfit 자체 클라이언트**(`packages/comfy`, 에디터와 같은 코드)로 Cloud에 한꺼번에 큐잉 → 198초 만에 15/15 완료 → 다운로드 → 맞춤. 스크립트 `demo/furnish-house.ts`.

**실데이터가 찾은 두 번째 근본 원인:** 15개 중 13개가 경고(왜곡 최대 4.12). 원비율을 재 보니 정면 사진으로 만든 소파만 표기 비율과 맞고, **3/4 각도 사진으로 만든 모델은 그 각도만큼 돌아간 채로 생성**돼 바운딩 박스가 정사각형에 가까웠다(주방 카운터 1.62:1.33 vs 표기 3.33:0.67). 가설을 스크립트로 먼저 검증(발자국 최소 회전 → 차 2.63→1.29) → 스펙 AC-36(자동 Y축 정렬)·AC-37(`auto` 모드: 정렬 후 왜곡 ≤1.15면 exact, 아니면 uniform). 실제 쇼핑몰 사진은 대부분 3/4 각도라 프롬프트가 아니라 맞춤에서 풀어야 한다.

**impl-09 (367초, $1.47):** 정렬·auto 구현. **세 번째 `BLOCKED:`** — 또 내가 계약(`ProductRequest.mode`에 `auto`, 리포트에 `requested`/`yawDegrees`)을 안 따라 고쳤다. 계약을 고치고, 패널 기본값 변경은 후속 세션으로.

**결과:** 15개 모두 정렬(각 ~75ms), 3개 exact·12개 uniform. 가구 15개가 실제 Cloud 생성물로 들어간 집이 스튜디오에서 문제 0건으로 배치됨.

**강의 포인트 24 — 하네스의 규칙은 시험지 밖에서도 작동한다.** 코딩이 아닌 "집 꾸미기" 세션에서도 Stop 훅·BLOCKED·보고 규칙이 그대로 적용됐다. 그리고 이번 BLOCKED도 원인은 사람: 에이전트가 일하는 체크아웃을 스펙 세션이 건드리면 안 된다.

**강의 포인트 25 — 비용 게이트가 계획을 바꾼다.** 에이전트는 막히자 사람에게 묻는 대신 비용 확인이 필요 없는 경로를 찾았다. 게이트 설계가 곧 에이전트 행동 설계다.

## 세션 16 — M5 스파이크와 승인, M6 Draft (2026-10-18)

- **M5 스파이크(단테 승인, Cloud 생성 3회)**: 레이아웃에서 침실 깊이 파노라마를 직접 레이캐스트(벽·창·문·가구 상자) → Qwen-Image 2512 + 360 LoRA + Lightning 4-step, 같은 프롬프트·시드로 제어 없음 / 깊이 0.6 / 0.9.
  - 제어 없음: 사진 같지만 **다른 방**(침대·의자 위치가 엉뚱함).
  - 0.6: 침대가 이음매를 감싸고, 의자·램프·옷장·창 2개·문이 레이아웃 그대로. **채택**.
  - 0.9: 의자가 상자가 됨. 제어를 세게 할수록 CG처럼 보인다.
  - 이음매를 숫자로: 첫 열과 끝 열 차이 2.8 vs 보통 이웃 열 3.3 → 보이지 않음.
  - 첫 깊이 인코딩(8m 선형)은 5m 방에서 거의 다 밝은 회색 → 40~600cm로 늘림. 스펙 규칙에 반영.
- **M5 Approved** (열린 질문 추천안), ADR-0010.
- **M6 Draft** — 단테 "로컬이랑 클라우드 선택? MCP도? 워크플로우도 같이 보면 좋겠다". 코드를 읽어 보니 백엔드는 서버 시작 시 환경 변수로 고정, **에디터는 항상 Cloud 워크플로를 보냄**(로컬 ComfyUI엔 Pixal3D/MoGe 노드가 없으면 실패). 그래서 스펙은 스위치 + 백엔드별 워크플로 세트 + `/object_info`로 실행 가능 여부 확인 + 작업 카드의 "Workflow" 패널(제출한 그래프 그대로).

**강의 포인트 26 — 스파이크는 같은 시드로 "제어 없음"을 꼭 같이 돌린다.** 제어 없는 결과가 더 예뻤기 때문에, 비교군이 없었다면 깊이 제어의 가치(=내 방이냐)를 설명할 수 없었다.

**강의 포인트 27 — 질문 하나가 숨은 결함을 드러낸다.** "로컬도 되나?"라는 질문에 답하려고 코드를 읽다가, 로컬에서 상품→3D가 실제로는 안 된다는 걸 찾았다. 스펙의 "왜"는 기능 요청이 아니라 이런 사실에서 출발한다.

## 세션 17 — M5·M6 구현, 실제 데이터가 잡은 규칙 구멍, M7 Draft (2026-10-18)

- **M5**: 스펙 세션(계약·Cloud 카탈로그 12개 노드·워크플로·파노라마 픽스처·가짜 Comfy·AC-63~68) → **구현 전 verify로 빨간 목록이 정확히 기대한 것뿐인지 확인**(새 습관) → impl-18(26분, $3.96). **6번째 BLOCKED = 내 테스트**: 8비트 깊이에서 수직 방향이 40열 폭의 평탄 구간인데 첫 열을 잡음. 에이전트가 픽셀을 읽어 구간이 정확히 중심에 있음을 보여 주고 수정안 2개 제시 → 중심값으로 고침, 구현 수정 0.
- **AC-69 실제 Cloud**: 48초 생성, 레이아웃 유지. 녹화가 결함 발견: **옷장(크고 밋밋한 깊이 판)이 뭉개짐** → 후속.
- **M6**: 스냅샷을 비교하다 발견 — 로컬 ComfyUI에도 Cloud 노드가 다 있다. 진짜 차이는 모델 파일·노드팩·입력 버전(`refine_steps`, 로컬용 MoGe 워크플로 추가). impl-19(18분, $4.20) BLOCKED 없이 통과.
- **실제 로컬 ComfyUI로 확인**: 모델이 하나도 없는데 3D 사진이 "준비됨". 원인 = 내가 쓴 규칙("비어 있지 않은 옵션 목록만 검사"). 실제 `/api/object_info`를 픽스처로 고정 → 빨간 테스트 → impl-20. **7번째 BLOCKED = 또 나**: 실제 카탈로그의 두 번째 형식(`["COMBO", {options}]`)과 가짜가 `*_name` 입력만 모델을 깔아 둔 것. 에이전트가 정확한 수정 지점을 짚음 → 적용, VERIFY PASS.
- **AC-76**(로컬·Cloud 같은 제품) 보류: 로컬에 모델 0개 → 모든 로컬 작업이 정확히 "불가"로 표시됨. 모델 ~25GB 다운로드는 단테 승인 필요.
- **M7 Draft**: 단테 "제품 사진·링크·어디 제품인지 바로 이동, 라벨링". 스키마에 `productUrl`이 있었지만 한 번도 쓰이지 않았다는 사실에서 출발.

**강의 포인트 28 — 빨간 목록부터 검증한다.** 스펙 세션 끝에 verify를 돌려 "기대한 AC만 빨갛다"를 확인한 뒤에야 구현 세션을 띄운다. 이후 BLOCKED는 테스트 자체의 결함으로 좁혀졌다.

**강의 포인트 29 — 가짜는 진짜 데이터에서 만든다.** 손으로 만든 가짜 카탈로그는 제품 버그를 숨겼고(빈 목록 = 설치 안 됨), 규칙을 고치자 이번엔 가짜가 깨졌다. 실제 ComfyUI의 응답을 픽스처로 고정하자 둘 다 드러났다.

**강의 포인트 30 — BLOCKED 7건이 모두 사람 쪽.** 시험지를 못 고치게 막은 장치가, 시험지를 쓴 사람의 실수를 일곱 번 정확히 보고하게 만들었다. 다음 개선 대상은 에이전트가 아니라 스펙 세션이다.

## 세션 18 — 로컬은 골라서 쓴다: AC-76 (2026-10-18)

- 단테 "왜 로컬 모델을 받아야 하나?" → 정직하게 답함: 필수 아님(제품은 Cloud로 충분), AC-76 녹화 때문, 내 "~25GB"는 어림이었고 전부면 50GB+. 단테가 **MoGe 하나만**(실제 662MB, Comfy-Org 공식) 받아 "3D 사진은 로컬, 나머지는 Cloud"로 결정 → AC-76 범위 변경을 스펙에 기록.
- 로컬 ComfyUI(MPS)에서 준비 상태: 3D 사진만 가능, 나머지 셋은 정확한 모델 파일 이름으로 불가.
- **녹화가 또 결함을 찾음**: 실제 Cloud 카탈로그는 Cloud가 실제로 돌리는 모델 파일(Pixal3D, Trellis 2, DINOv3)을 목록에 안 넣는다 → impl-20의 엄격한 규칙 때문에 "Cloud · 1 workflow unavailable". 실제 Cloud 카탈로그를 픽스처로 고정 → Cloud는 노드 클래스만 → impl-21(9분, BLOCKED 없음).
- 재녹화: Cloud 렌더 11초 → Local로 전환 → 로컬 MoGe 3D 사진 7.4초 → 작업별 Workflow 대화상자. 작업 기록에 `render: cloud`, `photo3d: local`.
- 가드 오탐 1종 더: "쓰기 힌트 어디든 + 보호 경로 언급 어디든"이라 보호 파일을 읽고 다른 파일을 쓰는 복합 명령이 막힘. 보수적 설계의 대가(오탐 = 재시도 1회, 미탐 = 시험지 수정)로 유지.
- 녹화가 찾은 작은 UX 결함 2개(메뉴가 Esc로 안 닫힘, Workflow 대화상자 제목 잘림) → 후속.
- 구현 세션 누계 21회 · 234분 · 1019턴 · $46.74.

**강의 포인트 31 — 같은 API라도 환경마다 진실이 다르다.** 로컬 `/object_info`는 "설치된 모델"을 정확히 말하지만, Cloud의 것은 말하지 않는다. 두 환경의 실제 응답을 각각 픽스처로 고정해야 규칙이 양쪽에서 맞는다(강의 포인트 21의 확장).

**강의 포인트 32 — "필요한가?"라는 질문엔 비용과 대안을 같이.** 25GB를 받자고 하기 전에 왜 필요한지, 정말 필요한지 물었어야 했다. 답은 "녹화 하나 때문"이었고, 662MB로 더 좋은 시연(골라 쓰기)이 됐다.

## 세션 20 — 실제 쇼핑몰 상품으로 AC-82 (2026-10-18)

- 단테 "아마존에서 소파 괜찮은거 골라서 해봐" → 내가 고름: HULALA 84″ 가죽(4.6★), Baxton Sorrento 회색(4.2★, 587), DOPEDIO 71″ 베이지(4.3★, 606). 상품 페이지에서 표기 크기(인치→cm)와 사진 확인.
- **실제 상품 사진은 연출 사진이 많다**: 3개 중 2개의 대표 이미지가 러그·커피 테이블이 있는 거실. HULALA는 흰 배경 3/4 컷을 찾아 쓰고, DOPEDIO는 연출 사진뿐이라 그대로 시험 → Pixal3D 워크플로의 배경 제거가 소파만 뽑아냄.

**강의 포인트 34 — 실데이터는 시연을 정직하게 만든다.** 내가 만든 AI 상품 사진(깨끗한 흰 배경)으로는 안 보이던 것들 — 연출 사진, 비율 왜곡, 쇼핑몰의 봇 차단 — 이 실제 상품 세 개로 한 번에 드러났다.
